# Stoat Voice — Discord-Parity Gap Audit (dev codebase)

**Date:** 2026-05-11
**Branch audited:** `stoat-web-dev` (the dev branch is the de-facto subject; prod has a substantially thinner pipeline already documented in `architecture-audit.md`).
**Scope:** Hunting for unknown-unknowns. Items already covered by existing beads or by `architecture-audit.md` / `target-architecture.md` are noted by reference, not re-investigated.
**Output:** Triage doc only — no code changes, no proposed architectural shifts (those belong to A2).

The audit re-ordered the user-suggested priority slightly: **TX toggle behavior** and **voice-UX state coupling** (deafen, notifications) surfaced more critical findings than auxiliary features. The two most severe items (deafen not auto-muting mic; mid-call device change silently ignored) are state-machine bugs, not architecture bugs.

Top recommendations by impact-per-effort:

1. **#1 (deafen ≠ mute)** — three-line fix; user-visible critical.
2. **#3 (mid-call PTT-enable)** — same fix pattern; same severity class.

4. **#8 (DF3 reload on slider)** — separate the level effect from the rebuild effect, call `setSuppressionLevel()` directly. The wrapper memory note already confirms this is exposed.
5. **#14 (decoration `loading="lazy"`)** — single attribute.

## Items where reference behavior is uncertain — flag for human

- **#10 (per-user mute = `setEnabled(false)`)**: Discord's exact behavior is anecdotal. If Stoat's "mute = stop receiving" is acceptable (less bandwidth, slight unmute-glitch), keep it. If users expect "mute = local silence only, packets still flow," needs change. **Pick one and document.**
- **#11 (forced subscribe)**: Lazy-subscribe matters at scale that Stoat may never hit. Defer or close as won't-fix.
- **#22 (speaking indicator latency)**: Whether local-user pulse should be driven from local-mic events vs. LiveKit's `useIsSpeaking` is a design call. Probably overlaps with existing bead **StoatData-3bs**.
- **#16 (custom decoration URL)**: How worried are we about a self-hosted-Stoat user using decorations to probe internal hosts? Threat model decision.
- **#25 (Firefox concealment stats undefined)**: Acceptable platform gap or worth a Firefox-specific code path?

## Items skipped due to budget

These were on the docket but not investigated thoroughly enough to land in the table:

- **Voice channel switch timing in detail** — only checked the disconnect→connect sequence at a high level; haven't verified there's no double-`playSelfJoin` race during a fast channel hop. Worth a 30-min targeted look.
- **App-audio (per-process capture) interaction with deafen / mute** — saw that it publishes as `Track.Source.ScreenShareAudio` and the renderer side has `pcm-feeder` worklets, but didn't trace the muted/deafened paths through that source class.
- **Screenshare audio compressor settings** — the per-track DynamicsCompressor uses the same `-24/4:1` settings for voice and screenshare audio (CompressedAudioTrack.tsx:84-88). Screenshare audio (music, game audio) probably doesn't want the same compression as conversational voice. Didn't quantify impact.
- **NotificationSoundsSettings UI vs. actual sound state** — checked that the master + per-sound toggles are persisted, but didn't verify the toggles correctly clear `currentlyPlaying` (could trap a "stuck playing" state).
- **Jukebox volume slider interaction with the voice-output-volume slider** — they're separate, which is correct, but no audit of whether toggling jukebox mute on deafen leaks state.
- **Mobile / touch UX** — entirely out of scope; Stoat-on-mobile is barely mentioned in the codebase.
- **Connection quality indicator** — `livekit-client` exposes `ConnectionQuality` which the code logs to console (state.tsx:949) but doesn't surface in UI. Already covered by existing bead **StoatData-pxs (Voice/F5)**.
